# Instrucciones de trabajo

- Limítate al prompt vigente; no adelantes fases ni modifiques archivos ajenos a la tarea. Una instrucción posterior explícita del usuario prevalece para esa tarea.
- Los prompts numerados se trabajan con Codex local en VS Code, en `C:\Users\Franz\Desktop\App web Estado de maquinas`. Antes de editar o validar, verifica con herramientas Windows y la raíz Git real. Si el ejecutor está en Cloud, WSL, SSH, un contenedor u otro checkout, detente e informa. No trabajes simultáneamente en Cloud y local sobre cambios pendientes de la misma tarea.
- Comienza todo bloque PowerShell con `Set-Location -LiteralPath 'C:\Users\Franz\Desktop\App web Estado de maquinas' -ErrorAction Stop`. Comprueba `$LASTEXITCODE` después de cada comando nativo; detente ante errores.
- Antes de editar, registra raíz, rama, `HEAD`, árbol, índice, identidad de `origin` sin credenciales e instrucciones `AGENTS.md` y `AGENTS.override.md` aplicables. Revisa estructura, historial e integración de la base; la ausencia de `origin` por sí sola no invalida el checkout, pero no permite afirmar sincronización remota.
- Preserva el trabajo previo. Ante cambios ajenos, una rama de otra tarea, divergencia o dudas sobre la base, informa y detente antes de editar. No uses `reset --hard`, `clean`, stash automático ni reescritura de historial como remedio rutinario.
- El usuario entrega cada número; Codex no inventa correlativos ni amplía el alcance. Cada tarea nueva usa el siguiente entero y una rama propia desde `main` sincronizado de forma segura, mediante avance rápido cuando corresponda. No edites directamente en `main`. Correctivos anteriores al merge: sufijos `A/B/C`, misma tarea y rama; después del merge: siguiente entero disponible.
- En local, ejecuta las pruebas, checks y builds pertinentes antes del Summary y de solicitar aprobación para publicar, respetando las restricciones del prompt. Distingue pruebas escritas, automatizadas ejecutadas, pendientes y revisión visual efectuada o pendiente. Registra comandos exactos, resultados y motivos de omisión; no atribuyas resultados históricos a la tarea actual.
- Para Django usa explícitamente `backend\.venv\Scripts\python.exe`, con variables locales sintéticas y restauración de las variables de proceso modificadas. Separa tests dirigidos, suite backend, `manage.py check` y `makemigrations --check --dry-run`; esta comprobación seca no autoriza generar ni aplicar migraciones. Valida frontend cuando el alcance lo requiera y consulta primero sus scripts reales.
- No uses `start.py` como diagnóstico, arranque o prueba habitual. Solo una tarea dedicada específicamente a revisar ese script puede autorizar su ejecución.
- No accedas a producción, uses secretos reales ni operes sobre datos reales. `migrate`, generación de migraciones, backfill, rollback, cargas, limpiezas o preparación de datos requieren alcance y autorización específicos. No instales ni restaures paquetes, alteres dependencias, herramientas globales o configuración personal como solución improvisada; requieren justificación y autorización.
- Antes de entregar, inspecciona internamente el diff completo, los cambios del índice y el contenido de los archivos nuevos, que no necesariamente aparece en `git diff`; contrasta todo con el alcance autorizado. El usuario entrega únicamente un Summary autosuficiente al coordinador, sin copiar aparte diff, parches ni logs y sin pegar el diff completo dentro del Summary. Si falta evidencia, se pide una aclaración concreta o una ampliación del Summary. Distingue la revisión local realizada por Codex de la revisión de su informe realizada por el coordinador.
- La implementación ordinaria no crea commit, push ni PR: un prompt separado, tras la revisión y aprobación del Summary, autoriza a Codex a realizarlos; el usuario no necesita hacer el commit manualmente. El usuario controla merge y despliegues. Tras el merge, sincroniza `main` de forma segura y verifica la integración, sin repetir suites completas ya aprobadas sobre el mismo contenido y entorno salvo causa concreta.
- “Apply changes and continue locally?” solo corresponde a una transferencia excepcional desde Cloud: revisa diff y estado, aplica una sola vez y verifica archivos, rama y `HEAD`. No lo uses para cambios ya hechos en VS Code local ni recibidos por merge y sync; no implica transferir commits ni autoriza publicar o integrar.
- Conserva el contexto arquitectónico: `ArriendoItem` aún no es fuente operativa autoritativa; termina y estabiliza Django antes de iniciar la edición .NET, con un futuro frontend compartido. Esto no autoriza funcionalidad multi-máquina.
- Termina con `# Summary` autosuficiente: identifica prompt, entorno, raíz, rama, `HEAD` y estado inicial; enumera todos los archivos creados, modificados o eliminados y explica por archivo los cambios relevantes y su finalidad, el antes/después y los contratos afectados cuando corresponda. Informa alcance revisado, desviaciones y trabajo previo preservado, pruebas escritas, comandos ejecutados con resultados, cantidades y códigos de salida, verificaciones omitidas o fallidas y motivos o errores sin secretos, revisión visual, riesgos y decisiones pendientes. Cierra con rama, `HEAD`, árbol, índice y situación de commit, push y PR; enlaza estos últimos solo si existen y están autorizados. Identifica los resultados históricos y no reproduzcas cada línea ni código completo.

Consulta [`docs/DEVELOPMENT_WORKFLOW.md`](docs/DEVELOPMENT_WORKFLOW.md) para el flujo detallado y los comandos de validación local.
